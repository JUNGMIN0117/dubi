- MapReduce는 데이터를 분산해 처리한 뒤 같은 Key를 기준으로 결과를 집계하는 구조다.

## 2026-08-26
### 한 일
- 이벤트 일정은 사전 확률을 조정하는 정보로 사용하고 실제 교통 데이터를 최종 판단 기준으로 사용하는 2단계 판정 구조를 정리했다.
- 누적 이력의 반복 실험, 이기종 스트림의 Event Time 처리, Kafka Replay와 배속 부하 테스트를 기준으로 분산 처리 필요성을 문서화했다.
- AI를 화면 기능이 아닌 데이터 파이프라인 내부에서 활용하도록 예측 모델과 베이스라인, 검증 지표를 정리했다.
- 서비스 MySQL과 Kafka·Parquet·Redis 파이프라인을 분리하고 두 영역을 `segment_id`로 연결하는 구조를 설계했다.
- 서비스 DB의 전체 DDL을 작성하고 ERDCloud에 임포트해 수기 ERD와의 충돌을 정리했다.
- 회원, 디바이스 토큰, 즐겨찾기 장소 테이블의 역할과 제약 조건을 검토했다.
### 배운 점
- 미래 이벤트 정보만으로 혼잡을 확정하지 않고 실측 데이터와 결합해야 취소나 일정 변경에도 안정적으로 대응할 수 있다.
- 분산 처리는 단순히 데이터 양이 많아서 사용하는 것이 아니라 장애 격리, 재처리, 시간 기준 집계와 반복 실험을 위해 필요하다.
- 서비스 데이터와 파이프라인 데이터를 분리하더라도 공통 식별자와 연결 책임을 명확하게 정해야 한다.
- ERD는 실제 조회·저장 방식과 데이터 변경이 과거 기록에 미치는 영향까지 고려해 설계해야 한다.

## 2026-08-27
### 한 일
- Backend 담당 팀원들과 서비스 DB 구조를 검토하고 테이블별 구현 범위를 정리했다.
- 외래 키 삭제는 애플리케이션 트랜잭션에서 자식부터 처리하고, 추천 결과는 재현성을 위해 INSERT-only로 저장하는 방향을 정했다.
- 알림 데이터 생성과 실제 푸시 발송을 분리하고 생성·수정 시각은 JPA Auditing으로 관리하도록 정리했다.
- 홈 대시보드, 일정 등록, 일정 상세, 실시간 지도, 알림 히스토리 화면의 흐름을 검토했다.
- 자체 길찾기 UI 대신 사용자가 아는 경로의 현재 상태를 보여주는 방식으로 지도 기능의 범위를 정리했다.
- 월간 캘린더 대신 오늘·예정·지난 일정과 주간 스트립을 사용하고, 지난 일정은 처방 결과 검증을 위해 보관하도록 했다.
- Jira에 서비스 정책과 DB ERD 작업을 등록하고 설계 결정과 근거를 문서화해 팀에 공유했다.
### 배운 점
- Backend 개발 전에 데이터 구조와 API의 책임을 합의하면 구현 중 발생하는 충돌을 줄일 수 있다.
- 알림 기록 생성과 외부 푸시 발송처럼 실패 조건이 다른 작업은 분리해 설계하는 것이 안전하다.
- 화면 기능 범위는 서비스가 해결하려는 핵심 문제와 수집 가능한 데이터에 맞춰 제한해야 한다.
- 협업에서는 결과만 공유하기보다 결정한 이유를 함께 기록해야 이후 변경 사항을 일관되게 판단할 수 있다.
