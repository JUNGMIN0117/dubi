## 2026-08-25
### 한 일
- Docker와 Docker Compose를 활용해 서비스별 실행 환경을 구성하는 방법을 공부했다.
- Kafka, Spark, Redis, MySQL, Spring Boot를 각각 컨테이너로 실행할 때 필요한 네트워크와 볼륨 구성을 조사했다.
- 환경 변수와 설정 파일을 이용해 로컬·개발 서버의 접속 정보를 분리하는 방법을 정리했다.
### 배운 점
- 컨테이너를 사용하면 팀원마다 다른 실행 환경에서 발생하는 문제를 줄일 수 있다.
- 컨테이너 간 통신에서는 `localhost`가 아니라 Compose 서비스 이름을 사용해야 한다.
- 데이터베이스와 메시지 브로커의 데이터는 컨테이너가 재시작돼도 유지되도록 볼륨을 연결해야 한다.
- 비밀번호와 API 키는 이미지나 저장소에 포함하지 않고 환경 변수로 주입해야 한다.

## 2026-08-26
### 한 일
- Kafka를 중심으로 데이터 수집기와 Spark 처리 작업을 연결하는 인프라 구조를 공부했다.
- Kafka 토픽, 파티션, Consumer Group이 데이터 처리량과 장애 복구에 미치는 영향을 확인했다.
- Spark 처리 결과를 Redis에 저장하고 Spring Boot가 조회하는 흐름을 정리했다.
- 원본·과거 데이터 보관과 Replay를 위해 HDFS 또는 Parquet 저장 영역을 구성하는 방안을 조사했다.
### 배운 점
- Kafka는 서비스 간 결합도를 낮추고, 처리기가 잠시 중단돼도 데이터를 다시 소비할 수 있게 한다.
- 파티션 수는 병렬 처리 수준과 연결되므로 예상 처리량과 Consumer 수를 고려해 정해야 한다.
- Redis는 최신 상태를 빠르게 제공하는 데 적합하지만 원본 이력의 영구 저장소로 사용해서는 안 된다.
- 실시간 처리 장애에 대비하려면 메시지 보관 기간과 오프셋 관리, Replay 절차를 함께 설계해야 한다.

## 2026-08-27
### 한 일
- GitLab CI/CD를 이용한 빌드·테스트·배포 자동화 방안을 공부했다.
- 서비스별 이미지 빌드 순서와 배포 시 의존 서비스의 준비 상태를 확인하는 Health Check 구성을 조사했다.
- 로그와 메트릭을 수집해 데이터 수집 지연, Kafka 적체, Spark 처리 실패, API 오류를 확인하는 모니터링 항목을 정리했다.
- 장애 발생 시 서비스 재시작, 데이터 Replay, 이전 이미지로 복구하는 운영 절차를 정리했다.
### 배운 점
- CI/CD는 단순히 자동 배포하는 기능이 아니라 동일한 검증 과정을 반복해 배포 오류를 줄이는 장치다.
- 컨테이너가 실행 중인 상태와 실제로 요청을 처리할 준비가 된 상태는 다르므로 Health Check가 필요하다.
- 분산 시스템은 한 서비스의 로그만 봐서는 문제를 찾기 어려워 공통 시간 기준과 추적 가능한 식별자를 사용해야 한다.
- 인프라 구축에는 정상 실행뿐 아니라 장애 감지, 재처리, 롤백 방법까지 포함되어야 한다.
